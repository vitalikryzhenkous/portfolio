## The problem: speed without shortcuts

The app answers one question for a tired parent at night: *what now, and when is the next sleep?* One-tap events,
the next sleep time, a calm night theme. Sleep calculations must match a sleep consultant's spreadsheet — a wrong
number at 3 a.m. is worse than no number.

Agents write most of the code. That only works if the process makes their usual failure modes hard: skipping the
spec, writing tests that mirror the implementation, declaring “done” without running checks, merging on red CI.

## Every feature runs the same 10-stage pipeline

1. **Plan** with a size (S / M / L) and open questions.
2. **Spec** written, then reviewed by a **spec-reviewer** agent with a fresh context (business + UX review), then my OK.
3. **Branch** from an up-to-date main.
4. **Tests first** — a **test-designer** agent sees only the approved spec, never the implementation.
5. **Implement** the smallest change that makes the tests pass.
6. **Verify** — a **verifier** agent runs tests, lint, types and the calculation-parity suite; fix until green.
7. **Review** — a **code-reviewer** agent checks the diff against the spec and the project rules.
8. **Commit & PR**, re-verifying if anything changed after stage 6.
9. **Deploy** — explicitly skipped until deployment is configured (no silent “done”).
10. **Metrics** — one row: date, task, model, minutes, accepted, notes.

The pipeline keeps its state per feature, so it can resume in any stage, in any session.

## Shortcuts are blocked by hooks, not by good intentions

| Hook | What it blocks |
|---|---|
| Commit gate | A commit of code without a green verify of **exactly this tree** |
| Merge gate | Merging a pull request unless every CI check is green |
| Agent sandbox | Reviewer and test agents can write only their reports (test-designer also test files) |
| Tool allowlists | Only the project's own CLI tools; `gh` limited to PR and issue commands |

CI runs the same checks: backend (lint, format, pytest) and mobile (lint, types, Jest — in two time zones, because
sleep spans midnight and daylight-saving nights exist).

## Design with a brief, and accessibility as tests

Screens go through a separate `/design` flow: a one-page brief (“night, one hand, half asleep”), 1–3 options, design
system additions, every state in light / dark / **night** theme and at the largest system font, then a hand-off spec.
Design system v1 shipped in 4 parts. A test computes colour contrast for the specified text/background pairs in
every theme (4.5:1 text, 3:1 controls); tap targets are at least 48 pt.

## What the log shows — honestly

- **Reviewers earn their keep:** 14 blockers and 41 should-fix items were raised by reviewer agents and addressed
  before the pull request.
- **Review is not perfect:** 15 spec bugs were still found after spec review, across 13 tasks — counted in the log,
  not hidden. One spec was rejected twice before the work started.
- **The phone catches what tests do not:** 11 task notes mention a check on a real phone; one of them (clipped hero text on
  a real device) became its own fix.
- **Time is an estimate:** minutes are mostly estimated active work and include waiting for my OK; they show
  relative effort, not productivity claims. Every task is marked accepted after my review; for UI tasks that usually included a phone check.
- **Known gap:** for one design-system part, VoiceOver and the largest font were not checked on a device (covered by
  tests and web instead); the device font check is tracked as an issue.

- **Measure escaped bugs per stage** (spec, tests, review, phone) to see which reviewer to strengthen next.
