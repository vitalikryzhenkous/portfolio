## The problem: private data vs. good answers

I use LLMs for everything, including text that should not leave my machine: national ID numbers, bank
details, health, contacts. Sending everything to the best cloud model is easy but leaks data and burns the
subscription limit. Sending everything to a local model is private but slow and often not good enough.

**jev decides per request**: what kind of task it is, how hard, and whether it is private — and routes it
to a local model or to the cheapest Claude model that can do it. The design goal: a sensitive request
must not reach the cloud, even when the text itself tries to talk the router into it.

## The LLM extracts features; code decides the route

<JevPipeline />

- **The LLM extracts features; code decides the route** (ADR-001). A model output can be wrong or
  manipulated; a routing table in code can be tested, replayed and diffed.
- **Cloud calls are tickets, not fallbacks** (ADR-003). A cloud call needs a ticket bound to the hash of the
  exact final prompt; a failed local call never silently retries in the cloud. Cloud runs through
  `claude -p` in safe mode with tools disabled, its own system prompt and a per-call budget fuse.
- **Two entry points, one pipeline.** A CLI (`jev`) and an OpenAI-compatible HTTP API with two virtual
  models, `jev-auto` and `jev-local` (ADR-011). The API checks the **whole transcript**, not only the last
  message, and a conversation that was ever sensitive stays local.

It runs on an Intel i5-9500T with no GPU, inside my private network; the API binds only to loopback.

<details class="more">
<summary>Deployment details — runtime, latency, API, console</summary>

- **Runtime:** Ollama on an Intel i5-9500T, no GPU, inside WSL. One 7B model stays resident; the API warms it
  up at start so the first answer after a reboot does not pay the 10–36 s cold load.
- **Measured on this CPU:** decode ≈ 6 tokens/s, prefill ≈ 30 tokens/s on an idle host. Every local run logs
  load, prefill and generation time separately, and time-to-first-token for streamed answers.
- **API:** a systemd service that **refuses to bind anything but loopback**; one Ollama slot, two cloud
  slots, a short queue and 429 beyond it.
- **Console:** a Next.js PWA in a hardened container (read-only, all capabilities dropped), reachable only
  inside my private tailnet. API keys stay on the server; chat history stays on the device (ADR-013).

## The run log never stores text

The run log is how I measure everything — so it was designed first (ADR-005):

- **Allow-list, not deny-list.** One JSON line per run, built field by field: decision, effective route,
  latency, config hash. Task text, answers, errors and file names are not in the schema.
- **A canary test** plants a marker in every free-text field and fails if it reaches the log.
- **Prompt ids are keyed hashes**, not plain hashes — a short prompt's plain hash can be guessed.
- Writing the log can never change a run's outcome, and every exit path logs exactly once.

## Every change goes through a preregistered experiment

Since the protocol was introduced (October 2026), every change to the model, prompt or policy follows it — the
earliest prompt versions were tuned on the dev set before that:

1. **Preregister** the question, the frozen test set (by hash), the metrics and the decision rule — committed
   *before* any run. {snap.jev.preregistrations} preregistrations so far.
2. **Run once**, no reruns. Each run carries the hashes of config, policy, injection layer and judge.
3. **Apply the rule as written**; post-hoc observations are labelled post-hoc and cannot flip a decision.
4. **Write the ADR** — including negative results.

Negative results are kept, not hidden: an LLM judge for answer quality was built twice and rejected twice
(agreement with my labels too low: κ 0.10 and 0.08, ADR-008/010); two later prompt revisions were rejected
and the earlier prompt stayed (prompt changelog).

### Decision by data, not by model size: 7B stayed, a code layer did the rest

**1 · Smaller models (L11, ADR-009).** On the CPU box I tested qwen3.5 4B and 2B against qwen2.5:7b for the
classifier. Neither passed the gates (injection, false “sensitive”), so 7B stayed. But the run exposed that
**7B itself failed the injection gate: 4 of 6 attacks steered it** — and that “0 leaks out of 10” was a
property of the layered system (rules, guard, policy), not of the classifier.

**2 · A deterministic layer instead of a bigger model (L12b, ADR-012).** I added a code layer before the
classifier that normalises text (Unicode tricks, homoglyphs, spaced letters) and fails closed when a message
claims its data is “fake” or “public”. Result on unseen attacks: **18/18 detected**, label-hijack and
cost attacks 1/12 → **0/12**, no hits on the existing 202-case corpus, p95 latency **1.53 ms**. The price: one
public case on the new holdout was failed closed (marked sensitive) by mistake.

**3 · A newer 9B model for answers (L13c, ADR-009 A1).** The local executor got ID-number checks wrong, so
the obvious move was a bigger model. The preregistered rule said: switch only if the 9B has ≤ 1/30 timeouts,
p95 ≤ 150 s, wins more blind writing comparisons, matches or beats 7B on the checks, and stays within the
language and memory limits.

- Blind writing comparison (12 pairs, I voted without knowing which model wrote which): **9B 5, 7B 5,
  both bad 2** — no quality edge for the bigger model.
- **Decision:** 9B rejected on latency alone (13/48 timeouts, p95 180 s). Instead, a **facts layer**:
  code computes the checksum verdicts and the model only explains them — 7B went from **12/18 to 18/18**.
  The 9B model was removed from the host.

### Then three smaller experiments on the local answer

**4 · Native chat messages (L13e, ADR-011 A1).** Follow-up turns were slow because the model re-read most of the
chat each time. Sending native chat messages, with the facts at the end of the last user message, brought the
prefix cache back. Time to first token fell from **11.4 s to 2.4 s**, ID checks went from 17/18 to 18/18, and blind
votes were 4 : 2 for the new format. The whole answer still takes about 25 s at ≈ 6 tokens/s, so the next lever is
answer length, not the cache.

**5 · Pinned facts, rejected (L13f).** Fixing each facts block to the turn where the number first appears cut the
prefill after such a turn from **6.1 s to 1.6 s**. It still failed the rule: dialogue facts 2/3 vs. 3/3, language
drift 11 vs. 9 of 66. The change stayed out, and so did a lower temperature. The arm also bundled pinning with a
language line, so the design cannot say which of the two caused the loss. Pinning alone is a later test.

**6 · A stop for language drift (L13g, ADR-009 A3).** L13f showed Chinese, Japanese or Korean characters in about
5% of local answers on these test sets, and neither a prompt line nor a lower temperature reduced it. So code now
ends the answer at the first such character, with an ellipsis, unless the user asked for that language. I replayed
282 saved answers through the real code. The stop fired in 16. Of those, 8 had a correct verdict that could be
scored, and **all 8 kept it**; none flipped. The other 266 stayed byte-identical. That n is small: the 95% lower
bound is about 68%, below the 80% I had set as the threshold, so the rule passed as written but the true rate is not
pinned down.

**The first live request found what the replay could not.** “po japonsku”, typed without the Polish letter, missed
the exemption, and a legitimate Japanese answer was cut. The saved answers held no such request, so no offline check
could have caught it. It was fixed the same day and recorded as an amendment.

**Known gaps, stated in the repo:** routing is not perfect — on an earlier frozen holdout the production
prompt still let 2 of 13 sensitive cases through to a cloud route, and one corporate-ticket pattern is a
documented miss. That is why privacy rests on several layers (rules, injection layer, guard, policy), not on
the classifier alone, and why the gaps are tracked instead of hidden.

Two more are open. Console streams sometimes break: 8 of 26 console requests in November ended with a
client-closed status (run log, 2026-11-03). That count also includes pressing Stop, and the cause is not found yet.
And the local model's Polish is weak: invented details and stray words still appear, which the stop above does not
catch. Measuring that against Sonnet is the job of the Arena pilot.

<p class="note">What this is not: I did not train or fine-tune these models. The gains come from routing
policy, prompt iterations, deterministic layers and evals around off-the-shelf models.</p>
